function mouseToImg(ev) {
  if (display.w === 0) return null;
  let rect = canvas.getBoundingClientRect();
  if (rect.width === 0 || rect.height === 0) {
    // Fix B fallback: <img> rect
    const img = document.getElementById("image");

**Impact analysis (this matters because the prompt asked whether `state.saveError = String(err)` catch can surface a `Cannot read property 'infos' of undefined` as a save failure):**

`flushSave` does NOT call any of these paths. The flow is:
```
flushSave → serializeLabel → JSON.stringify(label) → bridge.invokeOp(...)
```
`JSON.stringify(null)` returns `"null"` (a string, no throw). The backend then would receive `"null"` as `label_text` and presumably error in `parse_label_text` / `serialize_label`. That backend error would propagate back through `bridge.invokeOp` and be caught by the `try/catch` in `flushSave`, surfacing as `state.saveError = "Error: parse_label failed: ..."` — but with the root cause being a backend parse error, not a frontend `Cannot read property 'infos' of undefined`.

The 9 unguarded accesses in main.js / canvas.js DO throw `TypeError: Cannot read properties of undefined (reading 'infos')` if the user clicks the canvas before any image has loaded (e.g. during initial app load, after a load failure, or if the IPC bridge delivers a label-less state for any reason). This surfaces as a console error in the click handler — it does NOT reach `state.saveError`. **It's a real bug, but not the specific save-failure mode the prompt described.**

Recommend: add `if (!state.label) return;` (or `return null;` / `return;` depending on the function) at the entry of `hitTestAnnotation`, `commitPolygon`, `deleteSelected`, the rect/keypoint click handlers, and the canvas `paintStatic`/`paintDynamic`. Severity: **major** (real bug, easy to hit, fix is one line per call site).
